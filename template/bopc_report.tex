\section{Exercise 3}

\subsection{What is the output of the three different versions?}

The different \texttt{\#pragma} functions only affect which thread executes what task, not the numerical computation. Therefore, res = 5 for \textsc{Version A}, \textsc{Version B} and \textsc{Version C}.

\begin{itemize}
	\item \textsc{Version A}: res = 5. There is no race because each task writes a different variable and \texttt{\#pragma omp taskwait} ensures that the parent thread does not read \texttt{a} and \texttt{b} before the writing is finished.
	\item \textsc{Version B}:  res = 5. Same as before, different tasks write to different variables and finish writing before they are read for \texttt{return}. One thread starts \texttt{res = omp\_tasks(5)}, the other threads work on tasks from \texttt{\#pragma omp task shared}.
	\item \textsc{Version C}:  res = 5. Each thread executes \texttt{res = omp\_tasks(5)} and overwrites the value, but the result is the same each time. 
\end{itemize}  

\subsection{How often is the function \texttt{omp\_tasks} called?}

For each v $\leq$ 2, \texttt{omp\_tasks = OT} is called once, for all larger v, it the number of calls depends on the two previous numbers. \\
OT(5) needs\\
\hspace*{5mm} OT(4) needs\\
\hspace*{10mm} OT(3) needs\\
\hspace*{15mm} OT(2)\\
\hspace*{15mm} OT(1)\\
\hspace*{10mm} OT(2)\\
\hspace*{5mm} OT(3) needs\\
\hspace*{10mm} OT(2)\\
\hspace*{10mm} OT(1)\\

\begin{itemize}
	\item \textsc{Version A}: \texttt{omp\_tasks}  gets called $ 1 \cdot OT(5) +1\cdot OT(4) +2\cdot OT(3) +3\cdot OT(2) +2\cdot OT(1)= 9$ times.
	
	\item \textsc{Version B}: Same as in Version A, \texttt{omp\_tasks}  gets called $ 1 \cdot OT(5) +1\cdot OT(4) +2\cdot OT(3) +3\cdot OT(2) +2\cdot OT(1)= 9$ times. \texttt{single nowait} and \texttt{task shared (b)} only affect which thread executes what and does not change the number of executions.
	
	\item \textsc{Version C}: Because of \texttt{\#pragma omp critical}, each thread executes \texttt{res = omp\_tasks(5)}. Thus, \texttt{omp\_tasks} gets called $ 3 \cdot 9 = 27$ times. 
	
	
\end{itemize}

\subsection{Convert OpenMP code to CUDA}
The \verb|kernel_gpu.cu| file has been modified in order to compute Jula sets on the GPU. We replaced the empty stub with three pieces: a \texttt{\_\_device\_\_} copy of \texttt{checkPointForJuliaSet} (the per-pixel escape-time loop, body unchanged from \texttt{kernel\_cpu.cpp}), a \texttt{\_\_global\_\_} kernel \texttt{julia\_kernel\_device} that derives its $(x, y)$ from \texttt{blockIdx}/\texttt{blockDim}/\texttt{threadIdx} and computes one pixel per thread, and a host-side \texttt{julia\_kernel} wrapper that picks a default $16 \times 16$ block size (or honors \texttt{--blocksize}), does \texttt{cudaMalloc} $\rightarrow$ kernel launch $\rightarrow$ \texttt{cudaMemcpy} back to the host buffer $\rightarrow$ \texttt{cudaFree}. The doubly-nested CPU loop disappears entirely --- its iterations are now expressed as the grid of threads launched on the GPU, with a bounds check inside the kernel to handle the case where the grid slightly over-covers the image.

\subsection{Impact of block size}
\label{sec:ex6-subtask3}
Now we fix the resolution to 2000x2000, and try out different block sizes. We can see that (1, 32) is the best block size. The output array is indexed as \texttt{julia\_set[x*res\_y + y]}, so adjacent values of \texttt{y} occupy adjacent memory locations. With block shape $(1, 32)$, all 32 threads in a warp share the same \texttt{x} but have consecutive \texttt{y} values, mapping to consecutive memory addresses --- the warp issues a single 128-byte L1 transaction (a fully coalesced write). With block shape $(32, 1)$, by contrast, threads share the same \texttt{y} but have consecutive \texttt{x} values, so their target addresses lie \texttt{res\_y} floats ($= 80\,000$~bytes) apart. The warp must then issue 32 separate L1 transactions, one per thread (fully non-coalesced).
